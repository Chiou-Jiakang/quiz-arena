# Quiz Arena — 產品需求文件（PRD）

- 文件版本：v1.0（MVP 規格基準）
- 文件日期：2026-10-15
- 專案階段：規格制定，尚未開始遊戲程式實作
- 預定產品版本：MVP v1.0.0
- 文件語言：繁體中文

## 1. 產品概述

**Quiz Arena** 是一款以多元知識問答為核心的單人網頁競技遊戲。玩家輸入暱稱，選擇知識類別與難度後，挑戰一場包含 10 題、每題限時 20 秒的四選一測驗。完成後可查看得分、正確率、逐題解析及排行榜。介面採深色科技競技場視覺風格，兼顧桌面與手機瀏覽器。

### 1.1 產品目標

1. 提供可完整遊玩的單人問答流程，含首頁、設定、作答、結算與再玩一次。
2. 以 Node.js / Express / SQLite 實作真實的前後端資料流及持久化資料。
3. 使用 GitHub 保留有意義的開發提交、版本紀錄及中文開發日誌。
4. 可在 Windows + VS Code 本機啟動、測試與演示。

### 1.2 目標使用者

喜歡知識問答、學生或一般網頁遊戲玩家；MVP 無須註冊。

### 1.3 主要成功判準

- 可從首頁開始、完成十題、查看結果並重新遊玩，正常流程不中斷。
- 有可用題庫、正確的限時與計分、可重啟的錯誤處理流程。
- 正式得分由後端計算，不能單純信任前端提交的總分。
- 成績寫入 SQLite，重啟伺服器後仍可查詢。
- 手機及桌面關鍵操作不溢出、不遮擋。
- 每次完成功能迭代均有測試與 Git 提交紀錄。

## 3. MVP 產品規格

### 3.1 首頁與開局設定

- 顯示產品名稱、簡短玩法、開始遊戲入口。
- 玩家輸入暱稱，進行前後端長度與格式驗證（建議 1–20 個可見字元；空白暱稱不接受）。
- 選擇題目類別與難度。初期類別可為單一類別或「綜合」；難度為簡單／中等／困難。
- 當選定題庫不足 10 題時，禁止開局並清楚提示原因，不暗中重複題目。

### 3.2 題目與作答

- 每局從符合篩選條件的已啟用題目中抽取 10 道不重複題目，順序每局可不同。
- 顯示題次（1/10～10/10）、題目本文及四個選項。
- 每題從開始顯示起計 20 秒。作答送出後不可修改，不接受重複提交。
- 答對／答錯／逾時有明確視覺回饋，可查看正解與簡短解析，再進入下一題。
- 瀏覽器端倒數用於即時顯示；**伺服器以自身時間驗證題目截止時間**，避免單純操控瀏覽器計時作弊。
- 為避免網路延遲誤判，伺服器收件時間、題目啟動時間與有效期以後端統一處理；實作前須將提示回饋與計時細節定案。

### 3.3 計分與結果

- 正確答案 +100，錯誤或逾時 +0；無速度加分、連擊獎勵或負分。
- 結算頁顯示總得分、答對題數、答錯／逾時題數、正確率與逐題解析。
- 提供重新遊玩與返回首頁。
- 玩家僅提交選擇的選項，不得提交可直接影響排名的自訂分數。

### 3.4 成績與排行榜

- 成績儲存於 SQLite；至少包含暱稱、分數、答對題數、題目類別、難度、完成時間和場次識別。
- 排行榜展示最近有效已完成場次的高分前 10 名；排序先以分數遞減，平分則以完成時間遞增（先達成者優先）。
- 同一暱稱不視為唯一身分，不承諾多人冒名防護；排行榜是休閒展示，不是具身分驗證的正式競賽。
- 僅在完成場次後列入排行；未完成場次不計分入榜。

### 3.5 響應式、易用性與錯誤回饋

- 桌面與手機寬度下均可操作，不出現主要內容橫向捲動或按鈕被遮擋。
- 使用明確對比色、可見的焦點狀態，且答題狀態不只靠顏色傳達。
- API、資料庫或網路失敗時呈現可理解的錯誤訊息及合理重試／返回入口。
- 重新整理或中途離開時 MVP **不保證恢復原場次**；未完成場次不列入排行榜。後續可擴充恢復機制。

## 4. 不在 MVP 範圍內

- 使用者註冊登入、密碼重設、社群登入。
- 即時多人對戰、聊天、WebSocket 房間。
- 付費機制、角色升級、成就或道具商城。
- AI 即時生成題目、玩家自行新增公開題目。
- 雲端上線、正式流量監控、跨裝置同步（可列為後續版本）。

## 5. 初步使用者流程

1. 進入首頁 → 輸入暱稱、選擇類別與難度。
2. 點擊開始 → 後端檢查題庫數量並建立場次。
3. 題目逐題展示 → 玩家於 20 秒內提交單一答案，或逾時。
4. 後端驗證作答、記錄結果並回傳正解、解析及目前得分。
5. 完成 10 題 → 後端結算、儲存分數。
6. 玩家查看結算與排行榜 → 可重新挑戰。

## 6. 技術方案與責任邊界

### 6.1 前端

- HTML：語意化頁面、表單、題目及結果呈現。
- CSS：深色科技風格、RWD、狀態提示。
- JavaScript：畫面狀態、DOM 事件、倒數視覺呈現與 `fetch()`。

### 6.2 後端

- Express：提供 JSON REST API、輸入驗證、題目抽取、場次狀態、截止時間驗證、答案驗證、計分與錯誤回應。
- 不對尚未作答的題目暴露正確答案；同場次不得重複結算／重複提交。
- 初期可採伺服器持有的暫時場次狀態搭配資料庫持久化；實作時應避免讓使用者任意指定場次分數。

### 6.3 SQLite

建議資料實體：

- `questions`：題目、類別、難度、四個選項、正解、解析、啟用狀態。
- `game_sessions`：唯一場次 ID、暱稱、類別、難度、建立時間、完成時間、狀態、累計分數。
- `session_answers`：場次 ID、題目 ID、選項、是否正確、是否逾時、作答時間。

資料表欄位、外鍵、唯一約束及索引於資料庫設計版本再正式確定。示範題庫採受控種子資料，避免引入版權或事實錯誤。

### 6.4 API 草案（實作前可調整）

| HTTP   | 路徑                     | 用途                                   |
| ------ | ------------------------ | -------------------------------------- |
| `GET`  | `/api/config`            | 取得可選類別與難度                     |
| `POST` | `/api/games`             | 依暱稱、類別與難度建立場次並取得第一題 |
| `POST` | `/api/games/:id/answers` | 提交作答，後端判定是否正確與是否逾時   |
| `GET`  | `/api/games/:id`         | 取得目前場次可公開狀態或完成結果       |
| `GET`  | `/api/leaderboard`       | 讀取排行榜前 10 名                     |

API 須定義一致的 HTTP 狀態碼與錯誤格式；此處為接口草案，非已完成實作。

## 8. 開發與版本治理

- 採「一個可驗證功能增量 → 本機測試 → 更新文件 → Git Commit → GitHub Push」循環。
- Commit 採 Conventional Commits，例如 `docs: define MVP requirements`、`feat: add quiz timer`。
- `README.md`：產品介紹、啟動指引、功能進度及最近更新。
- `CHANGELOG.md`：依版本統整新增／修正項目。
- `docs/DEVLOG.md`：每次開發日期、目標、修改檔案、測試結果、待解問題、Commit SHA。
- 不捏造開發日期、Commit、測試結果；提交時間以 Git/GitHub 實際紀錄為準。
- 版本里程碑（可依進度調整）：環境與文件 → 靜態 UI → 單機遊戲 → API → SQLite → 全端整合 → QA → MVP Release。

## 9. 未決事項（不阻礙建立文件）

1. 題庫每個類別、難度的初始數量與內容品質檢查；建議每個可選組合至少 10 題。
2. 每題結算回饋是否暫停到玩家手動點擊「下一題」（建議是）。
3. 排行榜是否混合類別與難度；MVP 可先全站排行，但需顯示類別／難度。
4. 暱稱可用字符、長度與敏感文字規則。
5. 最終部署平台及正式版的安全、資料備份與監控要求。

## 10. 變更管理

任何核心規則（計時、分數、題數、玩家身分、驗證責任）變更，應先更新本文件，再於 CHANGELOG / DEVLOG 記錄原因及對應 Commit。
